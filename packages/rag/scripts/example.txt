template-electron プロジェクト概要

このプロジェクトは Electron + Vite + React + TypeScript を基盤としたデスクトップアプリケーションテンプレートである。Electron のメインプロセスとレンダラープロセスの間を独自の型安全な IPC フレームワークで接続し、認証・AI チャット・MCP サーバー・家計簿デモ・UI コンポーネントギャラリーなど多数の機能を実装している。

========================================
ビルドシステムとパッケージ管理
========================================

パッケージマネージャーには pnpm を採用している。主なスクリプトは以下の通り。

- pnpm dev: Vite 開発サーバーを起動し、vite-plugin-electron を通じて Electron も同時に起動する。HMR（Hot Module Replacement）によりレンダラーの変更は即座に反映される。
- pnpm build: vite build でレンダラーをビルドし、tsc で型チェックを行い、electron-builder でパッケージングする。
- pnpm test: tsc --noEmit で型チェックした後、vitest run でテストを実行する。
- pnpm lint: tsc --noEmit と oxlint を順に実行する。
- pnpm check: tsc --noEmit、oxfmt、oxlint --fix を順に実行するオートフィックスコマンド。
- pnpm format: oxfmt でコード整形を行う。
- pnpm serve: Vite のプレビューサーバーでビルド済みレンダラーを確認する。

postinstall フックでは electron-builder install-app-deps が自動実行され、better-sqlite3 などのネイティブ依存がプラットフォームに合わせてリビルドされる。

ビルド出力先は dist/（レンダラー）、dist-electron/（Electron メイン・プリロード）、release/（パッケージ済みアプリ）の3つに分かれる。

========================================
Vite 設定
========================================

vite.config.ts では以下のプラグインが構成されている。

1. @tailwindcss/vite: Tailwind CSS v4 をネイティブに統合する。PostCSS を経由せずビルドパイプラインに直接組み込まれる。
2. @vitejs/plugin-react: React 対応。Babel プラグインとして babel-plugin-react-compiler を条件付きで有効にしている。ソースマップが必要なデバッグモードでは React Compiler を無効化し、ブレークポイントの正確性を保つ。
3. vite-plugin-electron: Electron のメインプロセスとプリロードスクリプトを Vite で一括ビルドする。メインプロセスのエントリは electron/main/index.ts、プリロードのエントリは electron/preload/index.ts。
4. TanStackRouterVite: TanStack Router のファイルベースルーティングを自動生成する。src/routes/ 配下のファイル構造からルートツリーを src/routeTree.gen.ts に出力する。

テスト環境は Vitest で構成されており、environment: 'jsdom'、globals: true の設定により、テストファイル内で describe、it、expect をインポートなしで使用できる。

========================================
TypeScript 設定
========================================

tsconfig.json では strict: true が有効であり、以下の追加チェックも含まれる。

- noUnusedLocals: 未使用のローカル変数を禁止する。
- noUnusedParameters: 未使用の関数パラメータを禁止する。
- noFallthroughCasesInSwitch: switch 文の fall-through を禁止する。
- noUncheckedSideEffectImports: 副作用インポートを明示的に管理する必要がある。
- verbatimModuleSyntax: import type と import を厳密に区別する。
- allowImportingTsExtensions: .ts 拡張子付きのインポートを許可する。

パスエイリアスとして @/* が src/* に、#/* が electron/* にマッピングされている。レンダラーコードでは @/ を、Electron コードでは #/ を使う規約になっている。

モジュール解決は bundler モードで、ESM（ECMAScript Modules）を前提とする。package.json の type フィールドは module に設定されている。

========================================
oxfmt 設定
========================================

.oxfmtrc.json では以下の設定が適用されている。

- semi: false（セミコロンなし）
- singleQuote: true（シングルクォート）
- trailingComma: all（末尾カンマ常時）

EditorConfig ではインデントにスペースを使用し、改行コードは LF、ファイル末尾に改行を要求している。

========================================
Electron メインプロセス
========================================

Electron のメインプロセスは electron/main/index.ts をエントリポイントとする。ここで AppContext 型が定義され、アプリケーション全体の共有状態を管理する。

AppContext は以下のフィールドを持つ。

- windowsById: Map<string, BrowserWindow> でウィンドウを ID で管理する。
- mcpServer: MCP サーバーインスタンス。
- db: better-sqlite3 の DataBase ラッパーインスタンス。
- authRuntime: 認証ランタイム（AuthRuntime）。

startApp 関数はジェネリックなアプリケーションライフサイクルマネージャーである。electron/main/app/startApp.ts に定義されており、初期化・ウィンドウ作成・破棄のライフサイクルを管理する。dispose パターンにより、アプリ終了時にリソースを確実に解放する。

ウィンドウ生成は electron/main/windows/createWindow.ts で行われる。セキュリティ設定として contextIsolation: true、nodeIntegration: false、sandbox: true、webviewTag: false が適用される。ナビゲーションポリシーにより許可されていない URL への遷移はブロックされ、window.open は常に拒否される。

タイトルバーは titleBarStyle: 'hidden' でカスタムタイトルバーを使用する。macOS 以外では titleBarOverlay が設定され、初期状態では透明で表示し、レンダラーからテーマ情報を受け取った後に色を更新する。

========================================
Context-per-Window パターン
========================================

各 BrowserWindow は固有の Context オブジェクトを持ち、WeakMap<WebContents, Context> で管理される。Context には以下のサブコンテキストが含まれる。

- theme: テーマ管理（ダーク/ライトモード）。
- mcp: MCP クライアント状態。
- aiChat: AI チャットセッション状態。
- kakeibo: 家計簿機能の状態。
- auth: 認証状態。

WebContents をキーとする WeakMap を使うことで、ウィンドウが閉じられると自動的にコンテキストがガベージコレクションされる。これによりメモリリークを防止している。

========================================
IPC フレームワーク
========================================

electron/shared/lib/ipc/ には独自の型安全な IPC フレームワークが実装されている。これが本プロジェクトの中核的なインフラストラクチャの一つである。

このフレームワークは以下の要素で構成される。

types.ts（型定義）:
- RecursiveMethodKeys: ネストされたオブジェクトからドット区切りのチャネル名を再帰的に生成する型。例えば { fs: { readFileAsText: () => string } } から 'fs.readFileAsText' というチャネル名が型レベルで導出される。
- PathValue: ドット区切りパスから対応する値の型を取得する。
- ExtractMethod: チャネル名から関数シグネチャを抽出する。
- WithWebContents: メインプロセス側でハンドラーに WebContents を注入する型。
- WithWebContentsApi: API 全体に WebContents を付与するユーティリティ型。

createResponseChannel.ts:
- イベント型の IPC で使用するレスポンスチャネル名を生成する。元のチャネル名に '::response' を付加する命名規則。

createElectronApi.ts（ブラウザ/プリロード側）:
- createElectronApi 関数でレンダラー側の API を生成する。
- useChannelAsInvoke ヘルパーで invoke 型（リクエスト/レスポンス）のチャネルを処理する。
- useChannelAsEvent ヘルパーで event 型（プッシュ通知）のチャネルを処理する。
- defineHelper 関数がコンパイル時にすべてのチャネル名が API 型と一致することを検証する。

createRegisterIpc.ts（メインプロセス側）:
- createRegisterIpc 関数で IPC ハンドラーを登録する。
- type: 'invoke' のエントリは ipcMain.handle で登録される。
- type: 'event' のエントリは webContents.send でレスポンスを送信する。
- イベント型では WeakMap を用いて WebContents 破棄時にリスナーを自動クリーンアップする。

deepMerge.ts:
- IPC 定義オブジェクトを深くマージするユーティリティ。複数の API モジュールを一つの定義に統合する際に使用する。テストファイル deepMerge.test.ts も存在する。

========================================
IPC API モジュール
========================================

IPC で公開される API は以下の7モジュールに分かれている。

auth.ts（認証 API）:
- auth.login: ユーザー名とパスワードでログインする。
- auth.logout: セッションを終了する。
- auth.getSession: 現在のセッション情報を取得する。

aiChat.ts（AI チャット API）:
- aiChat.sendMessage: メッセージを送信し、AI からの応答ストリームを開始する。
- aiChat.on.chunk: ストリーミングレスポンスのチャンクをイベントとして受信する。UUID ベースのリクエスト相関で複数の同時会話を区別する。

mcp.ts（MCP 管理 API）:
- mcp.startServer: MCP サーバーを起動する。
- mcp.stopServer: MCP サーバーを停止する。

kakeibo.ts（家計簿 API）:
- kakeibo.getExpenses: 家計データを取得する。expense_view という SQL ビューから読み取る。

fs.ts（ファイルシステム API）:
- fs.readFileAsText: テキストファイルを読み取る。
- fs.writeFile: ファイルを書き込む。
- fs.showOpenDialog: ファイル選択ダイアログを表示する。
- fs.showSaveDialog: 保存ダイアログを表示する。
- その他計10メソッドを提供する。

theme.ts（テーマ API）:
- theme.setTheme: テーマを設定する（dark/light/system）。
- theme.on.updated: テーマ変更イベントをレンダラーに通知する。

web.ts（Web API）:
- web.findInPage: ページ内検索を実行する。
- web.on.focus / web.on.blur: ウィンドウのフォーカス/ブラーイベントを通知する。

========================================
プリロードスクリプト
========================================

electron/preload/index.ts は contextBridge.exposeInMainWorld を使用して window.api オブジェクトをレンダラーに公開する。createElectronApi 関数で生成された型安全な API がそのまま露出される。

electron/electron-env.d.ts で Window インターフェースに api プロパティの型宣言を追加しており、レンダラー側で window.api にアクセスする際に完全な型補完が効く。

========================================
レンダラーアーキテクチャ
========================================

レンダラーのエントリポイントは src/main.tsx である。ここで React のルートが作成され、以下のプロバイダーがネストされる。

- QueryClientProvider: TanStack Query のクライアントを提供する。
- ThemeProvider: ダーク/ライトテーマの管理。Electron 環境では IPC を通じてメインプロセスとテーマ状態を同期する。
- DesignProvider: スタイルテーマ（lyra、maia、mira、nova、vega）の管理。
- AuthProvider: 認証状態の管理。
- RouterProvider: TanStack Router のルーターを提供する。

TanStack Router は createHashHistory() を使用するハッシュベースのルーティングを採用している。これは Electron の file:// プロトコルではブラウザの History API が使えないためである。

========================================
デュアル API レイヤー
========================================

src/api.ts は Electron 環境とブラウザ環境の両方で動作する統一 API レイヤーを提供する。

Electron 環境（window.api が存在する場合）では、プリロードスクリプトが公開した IPC ベースの API をそのまま使用する。ブラウザ環境（window.api が存在しない場合）では、モック実装を提供するか、Electron 専用機能についてはエラーをスローする。

これにより、レンダラーのコンポーネントは実行環境を意識することなく統一的に API を呼び出せる。開発時にブラウザで直接レンダラーを開いてデバッグすることも可能になる。

========================================
ルーティング構造
========================================

TanStack Router のファイルベースルーティングにより、src/routes/ 配下のファイル構造がそのままルート定義になる。

- /: ホームページ（パブリック、認証不要）。
- /login: ログインページ。認証済みの場合はリダイレクトされる。
- /(app)/: 認証が必要な保護されたレイアウトルート。TanStack Router の beforeLoad フックで認証チェックを行い、未認証の場合は /login にリダイレクトする。
- /(app)/demo/: デモ機能のレイアウト。
- /(app)/demo/ (index): ダッシュボード画面。
- /(app)/demo/tanstack-query: TanStack Query のデモ。
- /(app)/demo/table: TanStack Table のデモ。データテーブルのソート・フィルタ・ページネーションを実装。
- /(app)/demo/fs: ファイルシステム操作のデモ。
- /(app)/demo/web: Web イベント（フォーカス/ブラー、ページ内検索）のデモ。
- /(app)/demo/kakeibo: 家計簿デモ。SQLite から家計データを読み取って表示する。
- /(app)/settings: 設定ページ。テーマ・スタイル・モードの切り替え。
- /(app)/ui/: UI コンポーネントギャラリーのインデックス。
- /(app)/ui/$component: 個別の UI コンポーネントデモ。$component は動的パラメータで、56種類のコンポーネントを切り替えて表示する。

========================================
認証システム
========================================

認証は完全にオフラインで動作し、SQLite データベースに保存される。データベースファイルは app.getPath('userData')/auth.db に配置される。

パスワードハッシュには Node.js の crypto.scrypt（scrypt KDF）を使用し、ソルトはランダム生成される。比較には crypto.timingSafeEqual を用いてタイミング攻撃を防止する。

データベーススキーマは auth_users テーブルと auth_sessions テーブルで構成される。auth_users にはユーザー名、ハッシュ化されたパスワード、ソルトが保存される。auth_sessions にはセッション ID、ユーザー ID、有効期限、is_current フラグが保存される。

初回ログイン時にユーザーが存在しない場合は自動的に新規ユーザーが作成される。明示的な登録フローは存在しない。セッションの有効期限は10年に設定されている。is_current フラグにより、同一ユーザーの複数セッションのうちアクティブなものを識別する。

AuthRuntime パターンが採用されており、dispose() メソッドでデータベース接続などのリソースを確実に解放する。

レンダラー側では AuthProvider コンポーネントが認証状態を管理し、useAuth フックで任意のコンポーネントから認証情報にアクセスできる。TanStack Router の beforeLoad フックで /(app)/ レイアウトルートにルートガードを実装している。

========================================
AI チャットシステム
========================================

AI チャット機能は @tanstack/ai、@tanstack/ai-ollama、@tanstack/ai-react を使用して実装されている。

使用可能なモデルは以下の通り。
- gpt-oss:20b-cloud
- gpt-oss:120b-cloud
- qwen3-vl:235b-cloud

いずれも Ollama ベースで動作する。

ストリーミングの仕組み:
1. レンダラーが aiChat.sendMessage を IPC 経由で呼び出す。
2. メインプロセスが Ollama API にリクエストを送信する。
3. レスポンスのチャンクが aiChat.on.chunk イベントチャネルを通じてレンダラーに逐次送信される。
4. UUID ベースのリクエスト相関により、複数の同時チャットセッションを正しく区別する。

src/lib/fetchIpcEvents.ts には TanStack AI の ConnectionAdapter のカスタム実装がある。これは AsyncQueue パターンを使い、IPC イベントの非同期イテレータプロトコルを TanStack AI の期待するインターフェースにブリッジする。

チャット UI は react-markdown と remark-gfm でマークダウンをレンダリングする。AI の思考過程（thinking）、ツール呼び出し（tool-call）、ツール結果（tool-result）はアコーディオンで折りたたみ表示される。

サーバーサイドツール:
- switch_theme_dark: テーマをダークモードに切り替える。
- switch_theme_light: テーマをライトモードに切り替える。
- clock: 現在時刻を返す（クライアントサイドツール）。

MCP ツールは動的にロードされ、組み込みツールとマージされる。

========================================
MCP（Model Context Protocol）統合
========================================

MCP サーバーは Express HTTP サーバーとして実装されている。@modelcontextprotocol/sdk の StreamableHTTPServerTransport を使用し、enableJsonResponse: true でJSON レスポンスモードを有効にしている。

デフォルトポートは 3030 で、チャットを開くと自動的に起動する。

登録されているデモツール:
- print_hello: 引数で受け取ったメッセージをログに出力する。
- change_theme: テーマをライトまたはダークに変更する。

electron/shared/lib/tanstack-ai-mcp/index.ts には mcpToTanStackAiTools ユーティリティが実装されている。これは MCP ツールを TanStack AI の ServerTool 形式に変換する。stdio、HTTP、transport、client の4つの接続モードをサポートする。

========================================
データベース
========================================

アプリケーションデータには better-sqlite3 を使用する。データベースファイルは data/kakeibo.db に配置される。

electron/main/features/db/db.ts に DataBase クラスが定義されている。これは better-sqlite3 の薄いラッパーで、以下のメソッドを提供する。

- query(): SELECT クエリを実行し結果の配列を返す。
- get(): 単一行を取得する。
- run(): INSERT/UPDATE/DELETE を実行する。
- exec(): 複数の SQL 文を実行する（マイグレーション等に使用）。
- close(): データベース接続を閉じる。

マイグレーションファイルは data/ ディレクトリに配置される。
- data/0001_init.sql: 初期スキーマ作成。
- data/0002_sample.sql: サンプルデータ投入。

家計簿機能は expense_view という SQL ビューからデータを読み取る。

認証用の SQLite データベースは別ファイル（auth.db）で、node:sqlite の DatabaseSync（同期 API）を使用する。アプリケーションデータベースとは独立して管理される。

electron-builder の設定では extraResources にデータベースファイルを指定しており、asar アーカイブの外側にデータベースファイルが配置される。これは better-sqlite3 がネイティブモジュールであり、asar 内のファイルに直接アクセスできないためである。

========================================
RAG ライブラリ
========================================

electron/shared/lib/rag/ には Ollama の embedding API を利用した RAG（Retrieval-Augmented Generation）ライブラリが実装されている。

ingest.ts（ドキュメント取り込み）:
- ingestDocuments 関数がテキストをチャンクに分割し、各チャンクの embedding ベクトルを取得してストレージに保存する。
- テキストチャンク化はデフォルトで900文字単位、120文字のオーバーラップで行われる。
- embedding 用にはさらに700文字以下のサブチャンクに分割する。
- embedding モデルは nomic-embed-text-v2-moe:latest を使用する。
- ingest 時のプレフィックスは 'search_document:' である。
- ストレージハンドラーはプラグイン方式で、node:sqlite のデフォルトハンドラー（createHandlersWithNodeSqlite）が内蔵されている。カスタムハンドラーも渡せる。
- onProgress コールバックでチャンク処理の進捗を外部に通知できる（未指定時は無音）。
- sliceWithOverlap ヘルパーで chunkText と splitForEmbedding のスライスロジックを共通化している。
- assertType アサーション関数で型ナローイング付きのバリデーションを行う。

retrieve.ts（コンテキスト検索）:
- retrieveRagContext 関数がクエリテキストの embedding を取得し、保存済みチャンクとのコサイン類似度を計算して上位 K 件を返す。
- retrieve 時のプレフィックスは 'search_query:' である。
- デフォルトの topK は6。
- cosineSimilarity 関数にはベクトル次元の一致チェックが含まれており、不一致時はエラーをスローする。
- ローダーもプラグイン方式で、node:sqlite のデフォルトローダーが内蔵されている。

scripts/rag/ 配下にはサンプルスクリプトが4つある。
- run-ingest-sqlite.ts: SQLite デフォルトハンドラーでの ingest 例。
- run-ingest-json.ts: JSON カスタムハンドラーでの ingest 例。ChunkEntry 型を導入して Array<any> を排除している。
- run-retrieve-sqlite.ts: SQLite デフォルトローダーでの retrieve 例。
- run-retrieve-json.ts: JSON カスタムローダーでの retrieve 例。

========================================
UI コンポーネントとスタイリング
========================================

UI コンポーネントは shadcn/ui ベースで、src/components/ui/ に56種類のコンポーネントがベンダーコードとして配置されている。これらは直接編集せず、ラッパーコンポーネントで拡張する方針である。

代表的なコンポーネント:
accordion, alert, alert-dialog, avatar, badge, breadcrumb, button, calendar, card, carousel, chart, checkbox, collapsible, command, context-menu, data-table, dialog, drawer, dropdown-menu, form, hover-card, input, input-otp, label, menubar, navigation-menu, pagination, popover, progress, radio-group, resizable, scroll-area, select, separator, sheet, sidebar, skeleton, slider, sonner, switch, table, tabs, textarea, toggle, toggle-group, tooltip など。

スタイリングには Tailwind CSS v4 を使用する。@tailwindcss/vite プラグインによりネイティブ統合されている。

クラスユーティリティとして class-variance-authority（CVA）、clsx、tailwind-merge を組み合わせて使用する。src/lib/utils.ts の cn() 関数がこれらを統合する。

アニメーションには tw-animate-css を使用する。

スタイルテーマは src/styles/ に CSS ファイルとして定義されている。
- lyra.css
- maia.css
- mira.css
- nova.css
- vega.css
- custom.css
- styles.css

DesignProvider コンポーネントがスタイルテーマの切り替えを管理する。設定ページからテーマ（dark/light/system）とスタイル（lyra/maia/mira/nova/vega）を変更できる。

サイドバーレイアウトは SidebarProvider で管理され、アイコンモードへの折りたたみに対応している。

========================================
Frame RPC
========================================

src/lib/frame-rpc.ts には親ウィンドウと iframe 間の認証状態通信を行う Frame RPC システムが実装されている。postMessage API を使用して、安全にクロスオリジン通信を行う。

これは設定画面や外部コンテンツを iframe で表示する際に、親ウィンドウの認証状態を iframe 側に伝達するために使用される。

========================================
カスタムプロトコル
========================================

electron/main/infra/registerCustomProtocol.ts では app:// カスタムプロトコルが登録されている。これは Electron のプロダクションビルドでレンダラーのアセットを安全に配信するために使用される。file:// プロトコルの代わりに app:// を使うことで、セキュリティポリシーの適用が容易になる。

========================================
コンテキストメニュー
========================================

electron/main/windows/createContextMenu.ts では右クリックコンテキストメニューが実装されている。テキスト選択時のコピー、入力フィールドでの貼り付け、開発者ツールの表示などの標準的な操作を提供する。

========================================
パス解決
========================================

electron/main/infra/paths.ts ではデベロップメント、プロダクション、asar パッケージの各環境でのパス解決を統一的に処理する。app.isPackaged や process.resourcesPath を使い分けることで、開発時とパッケージ後で同じコードが動作する。

========================================
electron-builder 設定
========================================

electron-builder.json5 で Windows（NSIS インストーラー）、macOS（DMG）、Linux（AppImage）向けのパッケージング設定が定義されている。

主な設定:
- appId: アプリケーション識別子。
- productName: アプリケーション名。
- asar: true（アプリケーションコードを asar アーカイブに圧縮）。
- extraResources: asar 外に配置するファイル（データベース等）。
- Win 向けの NSIS 設定: ワンクリックインストール、ユーザーごとのインストール先。
- Mac 向けの DMG 設定。
- Linux 向けの AppImage 設定。

========================================
テスト規約
========================================

テストフレームワークには Vitest を使用する。設定は vite.config.ts 内で行われている。

テスト環境は jsdom で、ブラウザ API のエミュレーションが提供される。globals: true により describe、it、expect などがグローバルで使用可能。

テストファイルの命名規則は *.test.ts または *.test.tsx。

React コンポーネントのテストには @testing-library/react を使用する。Testing Library の推奨するユーザー中心のテストアプローチに従う。

フェイクタイマーを使用する場合は必ず vi.useRealTimers() で復元する規約がある。

========================================
セキュリティ
========================================

Electron のセキュリティに関して以下の対策が実施されている。

ウィンドウ設定:
- contextIsolation: true（プリロードスクリプトとレンダラーのコンテキストを分離）。
- nodeIntegration: false（レンダラーから Node.js API へのアクセスを禁止）。
- sandbox: true（レンダラープロセスをサンドボックス化）。
- webviewTag: false（webview タグの使用を禁止）。

ナビゲーションポリシー:
- 許可されていない URL へのナビゲーションをブロック。
- window.open による新規ウィンドウの作成を常に拒否。

IPC:
- レンダラーは Electron モジュールを直接インポートできない。window.api または src/api.ts を通じてのみメインプロセスと通信する。
- IPC ハンドラーではシリアライズ可能なエラーのみをスローする。生のオブジェクトをスローしてはならない。

パスワード:
- scrypt KDF によるハッシュ化。
- ランダムソルト。
- タイミングセーフ比較。

========================================
コードスタイルガイドライン
========================================

インポート:
- ESM インポートを使用する。
- import type を型のみのインポートに使用する。
- インポートは以下の順序でグループ化する: Node.js 組み込み → 外部パッケージ → 内部エイリアス（@/、#/）→ 相対インポート → 副作用インポート（CSS）。

命名規則:
- React コンポーネント: PascalCase。
- フック: useX。
- 関数・変数: camelCase。
- 型・インターフェース: PascalCase。
- 定数: SCREAMING_SNAKE_CASE（真に定数の場合）、それ以外は camelCase。

エラーハンドリング:
- 境界でアクション可能なメッセージとともに早期に失敗する。
- Electron メインプロセスでは IO と初期化処理を try/catch で囲み、コンテキスト付きでログを出力してから再スローする。
- IPC ハンドラーではシリアライズ可能なエラーのみをスローする。

フォーマット:
- oxfmt に任せる。手動フォーマットは行わない。
- 長い呼び出し引数や JSX プロパティは複数行に折り返すスタイルが一般的。
